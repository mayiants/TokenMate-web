## 一、ai-portal-go

### 1.1 CRITICAL - 安全风险

#### S1: 密钥泄露到 Git 仓库

**严重程度**: CRITICAL  
**文件**: `.env:12,18,22,37,49-54`, `.env.go-platform:39`

`.env` 和 `.env.go-platform` 包含生产环境密钥（DB_PASSWORD、JWT_SECRET、REDIS_PASSWORD、ENCRYPTION_KEY、SMTP 密码）已提交到 git 仓库。`.gitignore` 虽已列出 `.env`，但文件已被追踪。

**影响**: 任何有仓库访问权的人可获取数据库、Redis、SMTP 完整权限，可伪造 JWT token，可解密所有上游 API key。

**建议**:
1. 立即轮换所有泄露的密钥
2. 使用 `git filter-repo` 或 BFG Repo-Cleaner 清理 git 历史
3. 确认 `.env` 不再被追踪: `git rm --cached .env .env.go-platform`

---

#### S2: 默认管理员密码硬编码

**严重程度**: HIGH  
**文件**: `cmd/server/main.go:535`

当 `ADMIN_PASSWORD` 环境变量为空时，回退使用 `<ADMIN_PASSWORD>`。生产模式虽要求 12+ 字符，但此密码刚好满足且过于简单。

**建议**: 启动时强制要求设置 `ADMIN_PASSWORD`，移除硬编码默认值。

---

#### S3: 密钥导出端点一次性返回所有明文密钥

**严重程度**: HIGH  
**文件**: `internal/routes/admin.go:1291-1345`

`exportKeyPoolKeys` 解密所有上游 API key 并以明文 JSON 返回。仅依赖 admin JWT 认证，无二次验证。

**建议**: 添加二次认证（如操作密码）、审计日志、导出限流。

---

#### S4: Webhook 签名验证可绕过

**严重程度**: MEDIUM  
**文件**: `internal/routes/webhook.go:83-86`

当 `PORTAL_SYNC_SECRET` 为空时，签名验证完全跳过。攻击者可注入使用记录、操纵计费。

**建议**: 生产环境强制要求设置此变量，空值时拒绝启动。

---

#### S5: 邮件模板 HTML 注入

**严重程度**: MEDIUM  
**文件**: `pkg/mail/mail.go:100-111`

`SendEnterpriseInvitation` 中 `enterpriseName` 和 `acceptURL` 直接拼接到 HTML，未做转义。

**建议**: 使用 `html.EscapeString()` 转义所有用户可控输入。

---

#### S6: 验证码使用非安全随机数

**严重程度**: HIGH  
**文件**: `internal/web/auth.go:21`

`generateCode()` 使用 `math/rand` 生成 6 位数字验证码（100 万种可能），非密码学安全。`internal/routes/auth.go:436` 使用 `uuid[:6]`（16^6 种可能）。

**建议**: 改用 `crypto/rand`，增加验证码长度或尝试次数限制。

---

#### S7: Metrics 端点无认证

**严重程度**: MEDIUM  
**文件**: `cmd/server/main.go:177-179`

`/metrics` 端点暴露内部运营数据（活跃用户、活跃 key、认证失败次数等），无任何认证。

**建议**: 添加 IP 白名单或 Basic Auth。

---

#### S8: CORS 默认允许所有源

**严重程度**: MEDIUM  
**文件**: `cmd/server/main.go:487`

`ALLOWED_ORIGINS` 为空时，CORS 设置 `Access-Control-Allow-Origin: *`。配合 cookie 认证，任意源可发起凭据请求。

**建议**: 生产环境必须配置 `ALLOWED_ORIGINS`，空值时拒绝启动。

---

### 1.2 HIGH - Bug / 逻辑错误

#### B1: Webhook INSERT 参数不匹配（潜在数据丢失）

**严重程度**: CRITICAL  
**文件**: `internal/routes/webhook.go:890-900`

`processRecord` 的 INSERT 语句有 27 个占位符（$1-$27），但传入参数可能不完整。这会导致 INSERT 失败或插入错误数据，直接影响计费。

**建议**: 立即验证 SQL 参数数量与占位符匹配。

---

#### B2: Webhook 缺少幂等性检查

**严重程度**: HIGH  
**文件**: `internal/routes/webhook.go:890`

使用记录插入无幂等性检查。Proxy 网络超时重试时，同一条使用记录会重复插入，导致用户余额重复扣除。

**建议**: 基于 `trace_id` 添加唯一约束或 UPSERT 逻辑。

---

#### B3: 速率限制器内存泄漏

**严重程度**: MEDIUM  
**文件**: `cmd/server/main.go:566-607`

内存 IP 速率限制器的 `buckets` map 永不清理，随时间无限增长。

**建议**: 添加 TTL 过期清理 goroutine，或使用带过期的缓存库。

---

#### B4: Redis 连接失败静默忽略

**严重程度**: MEDIUM  
**文件**: `internal/db/db.go:75-79`

Redis 连接失败仅记录警告，应用继续启动。依赖 Redis 的功能（验证码、限流、队列、暴力破解防护）会静默失效。

**建议**: Redis 不可用时应明确降级策略或拒绝启动。

---

#### B5: CSRF Cookie 缺少 SameSite 属性

**严重程度**: MEDIUM  
**文件**: `internal/web/middleware.go:45`

CSRF cookie 未设置 `SameSite`，浏览器默认行为不一致。

**建议**: 显式设置 `SameSite=Lax` 或 `SameSite=Strict`。

---

### 1.3 MEDIUM - 架构 / 设计问题

#### D1: main.go 过于臃肿

`cmd/server/main.go` 608 行，`main()` 函数约 440 行，包含路由注册、中间件配置、后台 goroutine、CORS、限流器、管理员初始化等。

**建议**: 拆分为 `routes.go`、`middleware.go`、`background.go`、`init.go` 等。

---

#### D2: 欢迎奖金/邀请码逻辑重复

- 欢迎奖金: `internal/routes/auth.go:227-268` vs `internal/web/auth.go:217-256`
- 邀请码: `internal/routes/auth.go:439-518` vs `internal/web/auth.go:413-475`

两处实现行为不一致（如 `used_count` 递增逻辑）。

**建议**: 提取为共享 service 层。

---

#### D3: 双计费路径导致收入泄漏

Webhook 处理有两条路径：
1. `processRecord`（同步回退）- 事务内完整计费
2. `processBillingBatch`（异步队列）- 批量计费

若异步路径失败进入死信队列（3 次重试），使用已记录但余额未扣除。

**建议**: 统一为单路径，或添加对账机制。

---

#### D4: 后台 goroutine 无 panic recovery

`cmd/server/main.go:334-343, 360-376, 440-449, 452-461` 多个后台 goroutine 无 `recover()`，任一 panic 会崩溃整个进程。

**建议**: 所有 goroutine 添加 `defer recover()`。

---

#### D5: 大量错误被忽略

整个代码库广泛使用 `_ = r.db.Exec(...)` 和 `_ = rows.Scan(...)` 模式，包括：
- `internal/routes/admin.go:417-419` (createProvider)
- `internal/routes/admin.go:443-457` (updateProvider)
- `internal/routes/apikeys.go:601-634` (updateKey)

**建议**: 至少记录错误日志，关键操作应返回错误。

---

#### D6: `go:embed` 使用 `**` 通配符

`web/embed.go:5` 使用 `templates/**/*`，但 `go:embed` 不支持 `**` 递归匹配。

**建议**: 改为 `templates/**/*.html` 或列出具体子目录。

---

#### D7: 模板错误泄露实现细节

`internal/web/handler.go:164` 将原始错误信息返回给客户端。

**建议**: 仅返回通用错误信息，详细错误记录到日志。

## 二、ai-proxy-go

### 2.1 CRITICAL - 安全风险

#### P1: Nonce 重放防护跨实例失效

**严重程度**: CRITICAL  
**文件**: `internal/auth/auth.go:453-464`

`isNonceUsed` 在 Redis 报错时静默回退到本地 map。多实例部署时，同一 nonce 可在不同实例重放。

**建议**: Redis 不可用时应拒绝请求，而非降级到本地检查。

---

#### P2: 加密密钥回退到 JWT_SECRET

**严重程度**: HIGH  
**文件**: `pkg/keypool/manager.go:419-24`

`ENCRYPTION_KEY` 未设置时，使用 `JWT_SECRET` 进行 AES-256-GCM 加密。违反密码学密钥分离原则。

**建议**: 强制要求独立的 `ENCRYPTION_KEY`，禁止回退。

---

#### P3: API Key 暴露在 URL 查询参数

**严重程度**: MEDIUM  
**文件**: `pkg/models/validator.go:171`

Google provider 的模型验证通过 URL query 传递 API key，会被记录到访问日志。

**建议**: 改用 Header 传递。

---

#### P4: Sync 端点接受 query 中的 secret

**严重程度**: MEDIUM  
**文件**: `internal/server/admin_handlers.go:453-456`

`x-proxy-secret` 为空时回退到 `c.Query("secret")`，secret 暴露在 URL 中。

**建议**: 仅允许 Header 传递。

---

#### P5: 默认 admin secret

**严重程度**: MEDIUM  
**文件**: `internal/config/config.go:338`

默认值 `"admin-secret"` 过于简单，虽有启动检查但不够严格。

**建议**: 空值或默认值时拒绝启动。

---

### 2.2 HIGH - Bug

#### PB1: 锁无关限流器竞态条件

**严重程度**: HIGH  
**文件**: `internal/ratelimit/ratelimit.go:52-81`

`AllowN` 的 CAS 循环仅保护 `lastUpdate`，不保护 `tokens`。在读取 `currentTokens` 和 CAS 之间，其他 goroutine 可能已消耗 token，导致 token 更新丢失。

**建议**: 将 token 读写也纳入 CAS 保护，或改用 `sync.Mutex`。

---

#### PB2: 并发限制器缺少 `c.Abort()`

**严重程度**: HIGH  
**文件**: `internal/server/server.go:46-56`

并发限制拒绝请求后返回 JSON 但未调用 `c.Abort()`，请求继续执行到 handler。

**建议**: 在 `c.JSON()` 后添加 `c.Abort()`。

---

#### PB3: 上游错误响应体丢失

**严重程度**: MEDIUM  
**文件**: `internal/server/handlers.go:574-612`

上游返回 4xx/5xx 时，代理返回通用错误信息 `"Upstream request failed"`，丢失了 provider 特有的错误详情。

**建议**: 转发上游原始错误响应体。

---

#### PB4: WriteTimeout 为 0

**严重程度**: MEDIUM  
**文件**: `internal/server/server.go:72`

`WriteTimeout: 0` 无写超时，卡住客户端可无限占用连接。虽然 SSE 流有 10 分钟 context 超时，但非流式响应无保护。

**建议**: 设置合理的 `WriteTimeout`（如 5 分钟）。

---

#### PB5: 空 Models 切片逻辑反转

**严重程度**: MEDIUM  
**文件**: `pkg/keypool/manager.go:2133-2136`

`GetAllKeysForModel` 中，`key.Models` 为空时跳过该 key。但根据代码注释和其他逻辑，空 Models 应表示"支持所有模型"。

**建议**: 空 Models 切片应匹配所有请求。

---

### 2.3 MEDIUM - 设计问题

#### PD1: 大量包级全局变量

`internal/server/handlers.go:71-100` 定义了 `deps`、`usageBuffer`、`upstreamUsageBuffer`、`rateLimiter`、`modelRegistry`、`keyPoolManager` 等十多个全局变量。

**建议**: 封装为 struct，通过依赖注入传递。

---

#### PD2: handleChatCompletions 过长

`internal/server/handlers.go:349-702` 约 350 行，包含路由、provider 选择、请求转换、上游调用、响应转换、计费、审计等。

**建议**: 拆分为 `routeRequest`、`callUpstream`、`processResponse` 等子函数。

---

#### PD3: 路由逻辑重复

Bedrock/Standard 路由模式在 `handleChatCompletions`、`handleEmbeddings`、`handleImageGenerations` 中重复实现。

**建议**: 提取为共享路由函数。

---

#### PD4: 多个独立 Redis 客户端

- `cmd/server/main.go:100-104` (主客户端)
- `internal/ratelimit/ratelimit.go:146-150` (限流器)
- `pkg/keypool/manager.go:443-447` (keypool)

各创建独立连接池，浪费连接。

**建议**: 共享单一 Redis 客户端实例。

---

#### PD5: 非 Chat 端点无请求体大小限制

仅 `handleChatCompletions` 有 10MB 限制，`handleEmbeddings`、`handleClaudeMessages` 等无限制。

**建议**: 统一添加请求体大小限制中间件。

---

#### PD6: 优雅降级允许 30 分钟过期访问

`internal/auth/auth.go:34,607` Portal 不健康时，缓存 claims 可使用 30 分钟。已撤销的 key 或余额耗尽的用户可继续访问。

**建议**: 缩短 TTL 或添加关键操作的实时校验。

---

`ai-proxy`、`server`、`proxy.log` 等已提交到仓库。`.gitignore` 虽已列出但文件已被追踪。

**建议**: `git rm --cached` 移除追踪。

#### C3: 已废弃方法未清理
