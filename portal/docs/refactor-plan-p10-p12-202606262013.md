# Plan: P1 #10-12 Architecture Decoupling + CI Automation

## Goal
Complete the remaining P1 architectural work for both repos and add the missing CI security/lint automation, then commit each phase after green tests.

## Scope
- **Portal (ai-portal-go)**
  - P1 #10: Extract duplicated billing/dashboard `usage_records` SQL into `internal/query/`.
  - Add `govulncheck` to the Portal CI workflow.
- **Proxy (ai-proxy-go)**
  - P1 #11: Replace package-global `server.Set*` dependencies with a single injected service facade.
  - P1 #12: Decompose `internal/server/handlers.go` (~3,531 lines) into per-concern files (chat, embeddings, images, audio, responses, status/admin, shared helpers).
  - Add `govulncheck` to the Proxy CI workflow and enable `golangci-lint` with a minimal, strict-but-realistic configuration.

## Recommended approach
Do the work in **four independent phases**. Each phase is self-contained and can be committed separately, minimizing risk and making rollbacks easy.

### Phase 1 — CI automation (low risk, no functional change)
1. Add a `govulncheck` step to `ai-portal-go/.github/workflows/ci-portal.yml` (after `go vet`).
2. Add a `govulncheck` step to `ai-proxy-go/.github/workflows/ci-proxy.yml` (after `go vet`).
3. Add a minimal `.golangci.yml` to `ai-proxy-go` and uncomment the `golangci-lint` step in `ci-proxy.yml`. To avoid a massive lint-fix detour, start with a focused linter set: `govet`, `staticcheck`, `errcheck`, `unused`, `gosimple`, plus `gofmt`/`goimports`. If the initial run surfaces too many pre-existing issues, the config will exclude the noisy ones until they can be fixed separately (tracked as P2 #23).
4. Verify locally: `govulncheck ./...` passes in both repos, and `golangci-lint run` runs to completion in Proxy.
5. Commit as "ci: add govulncheck and enable golangci-lint".

### Phase 2 — Portal billing/dashboard SQL extraction (P1 #10)
1. Audit duplicated `usage_records` SQL in `internal/routes/billing.go` and `internal/routes/dashboard.go`.
2. Extend `internal/query/usage.go` / `internal/query/billing.go` with helpers that return structured data:
   - `GetUsageSummary(ctx, db, userID string, days int) ([]DailyUsage, TotalSummary, error)`
   - `GetUsageRecords(ctx, db, userID string, filters UsageRecordFilter) ([]UsageRecord, error)`
   - `GetUsageDistribution(ctx, db, days int, groupBy string) ([]DistributionRow, error)`
   - `GetDashboardStats(ctx, db, days int) (DashboardStats, error)`
   Keep response formatting, JSON shapes, and HTTP status handling in the route handlers.
3. Replace inline SQL in `billing.go` and `dashboard.go` with the new helpers.
4. Add unit tests for the new query helpers against Postgres (similar to existing `internal/query/*_test.go`).
5. Run `go vet ./...`, `go test -race ./internal/routes/... ./internal/query/...`, and `gofmt -l .`.
6. Commit as "refactor(portal): extract usage_records queries into internal/query".

### Phase 3 — Proxy dependency injection (P1 #11)
1. Introduce `internal/server/handler_service.go` with a `HandlerService` struct holding:
   - `logger`, `cfg`, `authMiddleware`, `rateLimitMiddleware`
   - `keyPoolManager`, `modelRegistry`
   - `usageBuffer`, `upstreamUsageBuffer`
   - `handlerDeps` (`HandlerDependencies`)
   - `serverID`
2. Add `NewHandlerService(...)` constructor.
3. Convert all package-level `Set*` globals (`SetKeyPoolManager`, `SetModelRegistry`, `SetHandlerDependencies`, `SetUsageBuffer`, `SetUpstreamUsageBuffer`, `SetServerID`) into fields on `HandlerService`.
4. Change `setupRoutes` to accept `*HandlerService` and register `service.handleXxx` methods instead of free functions.
5. Update `cmd/server/main.go` to construct one `HandlerService` and pass it to `server.New`.
6. Keep behavior identical; no logic changes.
7. Verify `go build ./...`, `go vet ./...`, `go test -race ./...` in Proxy.
8. Commit as "refactor(proxy): inject HandlerService dependencies instead of package globals".

### Phase 4 — Proxy handler decomposition (P1 #12)
With all handlers now methods on `HandlerService`, mechanically split `handlers.go` into smaller files:
- `handlers_chat.go`: `handleChatCompletions`, `handleCompletions`, `handleClaudeMessages`, `handleAnthropicToOpenAI`, `handleAnthropicStreamingResponse`, `handleStreamingResponse`, plus chat-specific helpers.
- `handlers_embeddings.go`: `handleEmbeddings`.
- `handlers_images.go`: `handleImageGenerations`.
- `handlers_audio.go`: `handleAudioTranscriptions`, `handleAudioTranslations`.
- `handlers_responses.go`: `handleResponses`, `handleResponsesStreaming`, `handleResponsesPassthrough`, `handleResponsesPassthroughStreaming`.
- `handlers_status.go`: status, provider, model, heartbeat endpoints.
- `handlers_admin.go`: admin stats, affinity cache, audit, key-pool CRUD endpoints.
- `handlers_common.go`: shared provider resolution, retry/fallback, usage recording, error-response builders, streaming utilities.

Rules:
- Only move code; do not change signatures or logic.
- Keep package-level helper functions where they are if they are pure and have no state; otherwise make them methods on `HandlerService`.
- Run `go build ./...`, `go vet ./...`, `go test -race ./...` after each file move.
- Commit as "refactor(proxy): split monolithic handlers.go into per-concern files".

### Phase 5 — Documentation update

   - Mark P1 #10, #11, #12 as **Fixed**.
   - Refresh the SQL-duplication and Proxy-handler-monolith weakness notes.
2. Commit as "docs: mark P1 #10-12 fixed".

## Risks & mitigations
| Risk | Mitigation |
|------|------------|
| Moving 3,500 lines of Proxy handlers introduces regressions. | Do P11 first (inject service) then P12 (move files); keep logic identical; rely on existing tests plus full build/vet/race run. |
| golangci-lint surfaces many pre-existing issues. | Use a minimal linter set and exclude noisy linters initially; document remaining fixes under P2 #23. |
| Query extraction changes route behavior subtly. | Keep JSON formatting in routes; add query tests; run route tests against Postgres. |
| Large commit conflicts with other work. | Phase commits are small and focused; stop after each phase if needed. |

## Outcome
After all phases: production code has no swallowed DB errors from inline SQL duplication in billing/dashboard, Proxy handlers are testable without package globals, CI automatically checks vulnerabilities and lint, and the review doc reflects the completed P1 items.
