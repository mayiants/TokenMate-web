## 1. System Architecture

### 1.1 Overall Design

The system is a two-tier AI API platform. The **Portal** (`ai-portal-go`) is the authoritative control plane: it owns all persistent state (users, billing, API keys, payment records, audit logs) and exposes a management UI and REST API. The **Proxy** (`ai-proxy-go`) is a stateless, high-throughput request gateway that forwards client calls to upstream AI providers (OpenAI, Anthropic, Gemini, DeepSeek, AWS Bedrock, etc.). The Proxy has no local database; it syncs all routing and auth data from the Portal at runtime.

```
Client App
    │
    ▼
ai-proxy-go  (Go, Gin)
    │  JWT / Portal API Key auth
    │  Rate limiting (multi-window token bucket)
    │  Key pool selection + circuit breaker
    │  Request conversion (OpenAI ↔ Anthropic)
    │
    ├──► Upstream AI Providers (OpenAI, Anthropic, Gemini, DeepSeek, Bedrock …)
    │
    │  Async: usage events, audit logs, health telemetry (HMAC webhooks)
    ▼
ai-portal-go  (Go, Gin)
    │  Postgres (pgx/v5, raw SQL)
    │  Redis (auth cache, job queue, brute-force protection)
    │  HTMX frontend
    │  Payment gateways (Stripe, Alipay, WeChat)
    ▼
PostgreSQL + Redis
```

Both services are designed to deploy as independent Docker containers. The Portal is also the payment and user-management layer; the Proxy is the performance-critical hot path.

### 1.2 ai-portal-go Architecture

| Layer | Technology |
|-------|-----------|
| HTTP framework | Gin |
| Database | PostgreSQL via `pgx/v5` (raw SQL, no ORM) |
| Cache / Queue | Redis (auth cache, OTP, rate limiting, email job queue) |
| Frontend | HTMX + server-rendered HTML templates |
| Migrations | Custom file-based migration runner |
| Payments | Factory-pattern gateway abstraction (Stripe, Alipay, WeChat) |
| Logging | `go.uber.org/zap` structured logging |
| DI | Explicit `AppDeps` struct threaded through route handlers |

Routes are organized per-concern (`routes/auth.go`, `routes/admin.go`, `routes/webhook.go`, `routes/apikeys.go`, etc.). Background jobs (email dispatch, exchange-rate sync) run as goroutines started at boot.

### 1.3 ai-proxy-go Architecture

| Layer | Technology |
|-------|-----------|
| HTTP framework | Gin |
| Config | Viper with env-var override and startup validation |
| Auth | JWT + Portal API key validation, in-memory cache, graceful degradation |
| Rate limiting | Multi-window token bucket (RPM/RPH/RPD/RPW + token equivalents) |
| Key pool | In-memory, portal-synced, Redis-persisted; sharded usage counters |
| Relay | Provider adapter interfaces (`pkg/relay/`) |
| Stream conversion | OpenAI ↔ Anthropic SSE (`pkg/convert/`) |
| Circuit breaker | Per-provider, lazily initialized via `sync.Map` |
| Observability | Async batched webhooks to Portal; fallback file log at `/var/log/ai-proxy` |
| Logging | `go.uber.org/zap` |

The design intent (per `ai-proxy-go-design-202604291600.md`) is to maximize code reuse from the `new-api` project, maintain 7-year audit compliance, and keep the Portal unchanged.

### 1.4 How They Interact

| Interaction | Direction | Mechanism |
|-------------|-----------|-----------|
| Key pool sync | Portal → Proxy | HTTP polling + Redis pub/sub |
| Auth validation | Proxy → Portal | HTTP (`/api/auth/validate`) with local 5-min cache |
| Usage reporting | Proxy → Portal | HMAC-SHA256 authenticated webhook (batch) |
| Audit log shipping | Proxy → Portal | HMAC-SHA256 authenticated webhook |
| Provider health telemetry | Proxy → Portal | HMAC-SHA256 authenticated webhook |
| Payment webhooks (Stripe/Alipay/WeChat) | Provider → Portal | HTTP POST to Portal webhook routes |
| Admin sync secret | Shared config | `PORTAL_SYNC_SECRET` env var used by both services |

The Proxy's graceful-degradation pattern (30-minute extended auth cache when Portal is unreachable) means the two services can operate independently for short outages.

## 2. Key Implementation Highlights

### 2.1 Portal Key Patterns

- **Explicit dependency injection via `AppDeps`**: All route handlers receive a single struct containing the DB pool, Redis client, logger, and service instances. No package-level globals in the route layer.
- **Parameterized SQL throughout**: Every database query uses `$N` placeholders; no string-interpolated queries in the data layer.
- **Custom migration runner**: File-based, sequential migrations with tracking table. Tested separately from application logic.
- **JWT signing method validation**: The Portal validates the `alg` header before accepting any JWT, preventing the `alg:none` attack.
- **Redis-backed brute-force protection**: Login attempts are counted and blocked in Redis with sliding-window TTLs.
- **Payment gateway abstraction**: Stripe, Alipay, and WeChat implement a common `PaymentGateway` interface, making future provider additions low-risk.
- **HMAC webhook auth with replay protection**: Outbound webhook calls include timestamp + HMAC-SHA256 signature; the Portal verifies both on receipt.

### 2.2 Proxy Key Patterns

- **Atomic model index**: `pkg/keypool/manager.go` uses `atomic.Pointer[ModelIndex]` — rebuilt after every portal sync — giving O(1) model→key lookups with zero reader-side locking during normal operation.
- **Sharded upstream usage counters**: 32 per-shard mutexes reduce lock contention on the hot per-key RPM/TPM tracking path.
- **Async batched telemetry with fallback**: Three independent buffers (`UsageBuffer`, `UpstreamUsageBuffer`, `ProviderHealthBuffer`) batch-flush to Portal webhooks. On Portal unavailability each falls back to a local file log, preserving billing data.
- **Graceful auth degradation**: `auth.Middleware` extends cached claims for up to 30 minutes when Portal is unreachable, avoiding hard dependency on Portal uptime.
- **Request affinity fingerprinting**: `pkg/cache/affinity.go` SHA-256s request bodies and uses the first 8 hex chars to route repeated identical requests to the same upstream key, maximizing prompt-cache hits.
- **Circuit breakers per provider**: `pkg/circuitbreaker/ProviderBreakers` lazily initializes per-provider `CircuitBreaker` instances, isolating upstream failures.
- **AES-256-GCM key encryption at rest**: The Redis snapshot format encrypts actual upstream API key values with AES-256-GCM + HKDF-derived keys.
- **Constant-time secret comparison**: `subtle.ConstantTimeCompare` used consistently in `auth.go`, `server.go`, and `admin_handlers.go`.

## 5. Code Quality Issues

### Portal

**QC-P01 — Duplicated `UsageRecord` struct**  
`routes/` and `services/` packages each define a `UsageRecord` struct that must be kept in sync manually. Extract to a shared `types` package.

**QC-P02 — Logger init error discarded**  
`bootstrap.go`: `zap.NewProduction()` error is silently discarded. Assign and check the error; fatal if logger cannot be created.

**QC-P03 — `db.MustExec` on non-critical operations**  
Login-timestamp updates use `db.MustExec`, which panics on transient DB errors. Use `db.Exec` and log the error instead.

**QC-P04 — Export rate limiter is a mutable package-level global**  
`admin.go` uses a package-level `exportLimits` map rather than Redis, inconsistent with the rest of the codebase and not shared across instances.

**QC-P05 — Fragile dynamic SQL in `updateGateway`**  
Dynamic SQL assembly via string concatenation is correct today but creates a maintenance trap for future contributors who may introduce SQL injection. Use a query-builder or a fixed update with all optional columns.

**QC-P06 — Email job queue has no retry or dead-letter mechanism**  
Failed email dispatch jobs are silently dropped. Add retry with backoff and a dead-letter queue or alerting.

**QC-P07 — Stale dependencies**  
`golang.org/x/crypto v0.19.0`, `gin v1.9.1`, `golang-jwt/jwt v5.2.0` are behind current releases. Enable Dependabot or schedule regular updates.

**QC-P08 — XML built by `fmt.Sprintf` in `WechatGateway.QueryOrder`**  
`pkg/payment/wechat.go`: XML assembled via string concatenation risks XML injection if any value contains `<`, `>`, or `&`. Use `encoding/xml` marshaling.

**QC-P09 — Rate limiter burst equals per-second rate**  
The burst capacity is set equal to the rate, which is likely unintentional and undocumented. Document the intended behavior or adjust.

**QC-P10 — User email in log message strings**  
`fmt.Sprintf("... %s ...", email)` embeds user-supplied email addresses in log messages. Use structured `zap.String("email", email)` fields instead.

**QC-P11 — `go:embed` uses unsupported `**` glob**  
`web/embed.go`: `//go:embed templates/**/*` — the `go:embed` directive does not support `**` recursive glob. Use explicit subdirectory paths.

**QC-P12 — `cmd/server/main.go` is 600+ lines**  
The `main()` function (~440 lines) mixes route registration, middleware setup, background goroutines, CORS, and admin initialization. Split into `routes.go`, `middleware.go`, `background.go`, and `init.go`.

**QC-P13 — Background goroutines lack panic recovery**  
Multiple goroutines started in `main.go` have no `defer recover()`. A panic in any of them crashes the entire process.

**QC-P14 — Duplicate registration/bonus logic**  
Welcome bonus and invitation-code logic are implemented independently in `routes/auth.go` and `web/auth.go` with behavioral differences (e.g., `used_count` increment). Extract to a shared service method.

### Proxy

**QC-X01 — Misnamed `lockFreeBucket` struct**  
`internal/ratelimit/ratelimit.go`: The struct uses `sync.Mutex`, not lock-free CAS. Rename to `tokenBucket` to avoid misleading future maintainers.

**QC-X02 — `handlers.go` is a 116 KB monolith**  
`internal/server/handlers.go` exceeds 3,000 lines and contains routing, relay, streaming, fallback, usage recording, and model selection. Split by concern: `chat_handler.go`, `embed_handler.go`, `stream.go`, `routing.go`.

**QC-X03 — README env var prefix is wrong**  
`README.md` documents env vars with an `AI_PROXY_` prefix (e.g., `AI_PROXY_SERVER_PORT`), but the actual code uses bare names (`PORT`, `DB_HOST`). Operators will be unable to configure the service using the README.

**QC-X04 — `stringsContains` wrapper is dead weight**  
`pkg/billing/billing.go` defines a one-line wrapper around `strings.Contains`. Delete it and call `strings.Contains` directly.

**QC-X05 — Stub audit methods return empty results silently**  
`internal/audit/audit.go`: `GetStats`, `Query`, and `Search` return empty zero-value results with no indication they are stubs. Return `ErrNotImplemented` or remove them from the interface.

**QC-X06 — `RecordRequest` silently drops `traceID`, `userID`, `apiKeyID`**  
`internal/audit/audit.go`: Three parameters accepted by `RecordRequest` are never written to `AuditEntry`. Callers believe these fields are persisted; they are not.

**QC-X07 — `min` builtin shadowed in `pkg/cache/affinity.go`**  
The project targets Go 1.24 (`go.mod`). The custom `min(a, b int)` function shadows the generic built-in and will cause compile warnings in future toolchain versions. Remove it.

**QC-X08 — Three independent Redis clients**  
`main.go`, `ratelimit/ratelimit.go`, and `pkg/keypool/manager.go` each create their own `*redis.Client`, consuming three separate connection pools against the same instance. Pass a single shared client via dependency injection.

**QC-X09 — Inconsistent caching primitives in `auth.go`**  
`keyCache` uses `sync.Map` while `balanceCache` uses `map` + `sync.RWMutex` in the same struct. Standardize on one pattern.

**QC-X10 — Typed `contextKey` constants defined but never used**  
`internal/server/handlers.go` defines typed context-key constants but uses bare `c.GetString("user_id")` strings throughout. Either use the typed constants or remove them.

**QC-X11 — `handleGetStatus` returns hardcoded `uptime: 99.9`**  
`internal/server/admin_handlers.go`: The hardcoded value is misleading in any status-page or monitoring integration. Compute or remove the field.

**QC-X12 — `handleSyncKeys` returns unbounded key list with health internals**  
`internal/server/admin_handlers.go`: `handleSyncKeys` serializes all keys including `KeyRuntime` failure history and cooldown timestamps with no pagination. Add pagination and strip internal runtime fields from the response.

**QC-X13 — `concurrentLimiter` middleware missing `c.Abort()` after rejection**  
`internal/server/server.go`: After returning a 429 JSON response, `c.Abort()` is not called, so subsequent middleware and the handler still execute. Add `c.Abort()`.

**QC-X14 — CI Go version mismatch**  
`go.mod` declares `go 1.23.0`; `.github/workflows/ci-proxy.yml` uses `go-version: '1.24'`. Align them.

**QC-X15 — `golangci-lint` step commented out in CI**  
The lint step in `ci-proxy.yml` is disabled pending creation of `.golangci.yml`. Create the config file and re-enable the step.

## 6. Strengths

### Portal

1. **Consistently parameterized SQL** — Every query in the data layer uses `$N` placeholders. No string-interpolated queries were found.
2. **Correct HMAC webhook auth with replay protection** — Outbound portal webhooks use HMAC-SHA256 over `timestamp + "." + body`, preventing both forgery and replay attacks.
3. **Well-tested migration system** — The custom file-based migration runner has its own test coverage and is isolated from application logic.
4. **JWT signing method validation** — The portal validates the `alg` header before accepting any JWT, closing the `alg:none` attack vector.
5. **Redis-backed brute-force protection** — Login attempt counting and blocking is handled in Redis with sliding-window TTLs, surviving restarts.
6. **Structured zap logging** — `go.uber.org/zap` is used throughout with structured fields (not string interpolation), enabling production log aggregation.
7. **Clean per-concern route architecture** — Route files are organized by domain (`auth`, `admin`, `webhook`, `apikeys`, `payment`), each receiving dependencies via `AppDeps`.
8. **Payment gateway abstraction** — Stripe, Alipay, and WeChat implement a common interface; adding a new provider does not require touching existing payment logic.
9. **Thorough config test coverage** — Env-var validation, default values, and production startup hardening are covered by unit tests.
10. **Production startup hardening** — Missing or weak env vars (empty `JWT_SECRET`, short `ADMIN_PASSWORD`) cause the server to refuse to start.

### Proxy

1. **Strong startup secret validation** — `cmd/server/main.go` rejects startup if `Admin.Secret` is empty, equals the default `"admin-secret"`, or is shorter than 32 characters. Same applies to `Portal.SyncSecret`.
2. **Constant-time secret comparison** — `subtle.ConstantTimeCompare` is used consistently for all secret validation, preventing timing attacks.
3. **API keys never stored in plaintext in the cache** — `internal/auth/auth.go` hashes all API keys with SHA-256 before using them as cache keys (`hashCacheKey`).
4. **Upstream key encryption at rest in Redis** — `pkg/keypool/manager.go` uses AES-256-GCM with HKDF-derived keys for the Redis snapshot format.
5. **Graceful auth degradation** — The 30-minute extended cache TTL during Portal outages is a well-designed resilience pattern that avoids hard coupling to Portal uptime.
6. **Sharded upstream usage tracking** — 32 per-shard mutexes in `pkg/keypool/manager.go` reduce lock contention on the hot per-key RPM/TPM accounting path.
7. **Circuit breakers per provider** — Clean, minimal closed/open/half-open implementation in `pkg/circuitbreaker/breaker.go`, lazily initialized, preventing cascade failures.
8. **Fallback log for billing durability** — Failed Portal webhook calls write to `/var/log/ai-proxy` for manual reconciliation, preventing billing data loss.
9. **Atomic model index swap** — `atomic.Pointer[ModelIndex]` in `pkg/keypool/manager.go` provides lock-free reads during normal operation with a consistent snapshot after each sync.
10. **Comprehensive config tests** — Full coverage of defaults, env var overrides, file loading, and validation edge cases in `internal/config/config_test.go`.
11. **Structured logging throughout** — `go.uber.org/zap` with structured fields used consistently, enabling log aggregation and filtering.
12. **SSRF protection on user-provided URLs** — `validateBaseURL` in `admin_handlers.go` blocks loopback, link-local, and private IP ranges (with the DNS-resolution gap noted in §4).
