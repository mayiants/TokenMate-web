#### `internal/server/handlers.go` (+399/−37)

**New additions:**

| Component | Lines | Description |
|-----------|-------|-------------|
| `responsesRouteCache` | +65 | Thread-safe cache (provider:model → passthrough decision), 1h TTL, 5-min cleanup loop |
| Passthrough routing in `handleResponses` | ~40 changed | Refactored to branch between passthrough and convert modes; uses `shouldUsePassthrough()` |
| `shouldUsePassthrough()` | +30 | 3-tier decision: Portal capabilities → route cache → default to convert |

| `handleResponsesPassthroughStreaming` | +120 | Streaming passthrough — SSE relay with usage extraction from stream lines |

**Key behavioral changes:**
- `handleResponses` now skips Chat Completions conversion when the model is Responses-only (capabilities from Portal sync)
- `request_body` is now set on the gin context for affinity cache fingerprinting (previously missing)
- Simulate check moved after model resolution (was before — fixes model resolution in simulate mode)
- Model resolution now uses the original Responses model name (not post-conversion hub model)

**Review notes:**
- The route cache `cleanupLoop` is started via a `func init()` in the package — this is a **package-level init side effect**. Since Go allows multiple `init()` functions and this one is in `handlers.go`, it will run on package import. This is functional but could be surprising; consider moving to an explicit `Start()` call invoked from `main`.
- `handleResponsesPassthrough` and `handleResponsesPassthroughStreaming` share significant boilerplate (URL construction, request building, error handling). A shared helper (`buildResponsesProxyRequest`) could reduce duplication by ~40 lines.

#### `pkg/relay/interface.go` (+6)

**New adaptor routing:**
- `amazon-*` prefix → AWS adaptor (SigV4 Bedrock Runtime)
- `amazon-mantle-*` prefix → OpenAI-compatible adaptor (Bearer token, Mantle)

This correctly routes the auto-generated per-region providers to the right adaptor.

#### `pkg/relay/providers.go` (+54)

**New: Auto-registered per-region providers**

- **33 Bedrock Runtime regions** (`amazon-{region}`) — SigV4 auth, `bedrock-runtime.{region}.amazonaws.com`
- **13 Mantle regions** (`amazon-mantle-{region}`) — Bearer auth, `bedrock-mantle.{region}.api.aws/v1`
- `amazon` preserved as alias for `us-east-1` (backward compatible)
- Registration happens in `init()` — no manual config needed

**Review notes:**
- Mantle region list (13) is a proper subset of Bedrock regions (33) — correct, as Mantle is only available in select regions
- The `init()` approach means these are always registered even if unused. For a standalone proxy binary this is negligible overhead. If memory becomes a concern, consider lazy registration.

## 3. Assessment

### What's Good

1. **Clean architecture** — passthrough vs. convert is decided early in the handler and the two paths are well-separated
2. **Portal-driven capabilities** — primary decision comes from synced model metadata, not hardcoded heuristics
3. **Graceful fallback** — route cache provides dynamic fallback for cases where Portal hasn't synced capabilities yet
4. **Full observability** — passthrough paths include audit logging, affinity recording, usage tracking, provider health, and circuit breaker integration
5. **Backward compatible** — existing convert path is fully preserved; `amazon` alias still works

### Concerns

| # | Severity | Description |
|---|----------|-------------|
| 1 | Low | `func init()` in `handlers.go` starts a goroutine for cache cleanup — implicit lifecycle management. Prefer explicit startup from `main.go`. |
| 2 | Low | `handleResponsesPassthrough` and `handleResponsesPassthroughStreaming` have ~60% code overlap. Extract shared HTTP proxy logic. |
| 3 | Info | `request_body` is now set via `c.Set("request_body", bodyBytes)` — verify this doesn't conflict with other middleware that may also set this key. |
| 4 | Info | The `responsesRouteCache` default behavior is "convert mode" — if a Responses-only model is used before Portal syncs its capabilities, the first request will fail and the cache will learn. Consider whether a configurable default (e.g. env var `RESPONSES_DEFAULT_MODE`) would be safer. |

### Recommendation

These changes look well-designed and ready to commit locally once the minor duplication concern (#2) is addressed. The feature enables a significant new capability (direct Responses API passthrough for Bedrock Mantle and other Responses-native providers) without breaking existing Chat Completions flow.
