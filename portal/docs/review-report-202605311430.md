## 一、项目概述

AI Platform Go 是一个 AI API 代理平台，由两个 Go 服务组成：

| 服务 | 端口 | 职责 |
|------|------|------|
| **ai-portal-go** | 3001 | 管理后台：用户认证、Key 管理、计费、上游 Key 管理、Web UI |
| **ai-proxy-go** | 8080 | API 网关：请求转发、模型路由、限流、Key 池管理 |

两个服务通过 HTTP Webhook + Redis Pub/Sub 通信，Portal 是数据源，Proxy 是无状态代理。

## 三、实现分析

### 3.1 ai-proxy-go 核心实现

**入口与生命周期** (`cmd/server/main.go`):
- 启动时强制校验密钥长度 ≥32 字符（line 42-50）
- 异步批量刷新：Usage 3s、Upstream Usage 30s、Provider Health 30s（line 130-142）
- 优雅关闭 30s 超时（line 170-198）

**请求处理流程** (`internal/server/handlers.go:367-726`):
1. 读取请求体（10MB 限制）
2. 解析 JSON → `GeneralOpenAIRequest`
3. 模型路由（单点/轮询/自动均衡）
4. `allowed_models` 白名单检查
5. Affinity 缓存获取偏好 Key
6. 双轨路由（Bedrock VIP / 标准）
7. 创建 Provider 适配器
8. 格式转换 → 上游请求
9. 提取 Usage → 计费 → 审计

**Key 池管理** (`pkg/keypool/manager.go`):
- 分片锁 + 原子计数器，高并发安全（line 319-375）
- 5 级 Key 选择：Tier → Model → RPM → Affinity → LRU
- 失败处理：401/403 立即失效、429 60s 冷却、10 次/10 分钟失效
- Redis 持久化使用 AES-256-GCM 加密（line 1752-1813）

**多 Provider 适配** (`pkg/relay/`):
- 接口驱动：`Adaptor` 接口定义 10+ 方法（line 15-36）
- 5 种认证方式：bearer、x-api-key、api-key、query、aws-sigv4
- 21 个 Provider 配置，前缀匹配自动检测模型归属
- AWS Bedrock 完整 SigV4 签名 + 多区域故障转移

**计费** (`pkg/billing/billing.go`):
- 支持缓存 Token 折扣计费（读 10%、写 25%）
- 异步批量上报 Portal（HMAC-SHA256 签名）
- 3 层余额扣除：Gift → Recharge → Balance

### 3.2 ai-portal-go 核心实现

**技术栈**: Gin + pgx/v5 + go-redis/v9 + go:embed + HTMX + Alpine.js + Tailwind CSS

**路由层** (最大文件):
- `admin.go` (2902 行) — 用户/Provider/Model CRUD、上游 Key 管理
- `enterprise.go` (2888 行) — 企业 CRUD、成员管理、邀请流程
- `models.go` (2331 行) — 服务模型生命周期、验证、EOL 管理
- `webhook.go` (1858 行) — Usage 录入、计费、队列处理

**API Key 处理**:
- 生成：`sk-wgit-{uuid}` 格式
- 存储：SHA-256 哈希 + AES-256-GCM 加密
- 验证：单条复杂 SQL JOIN 查询 + Redis 缓存（5 分钟 TTL）

**计费系统**:
- 双余额：`gift_balance`（赠送）+ `recharge_balance`（充值）
- 企业信用额度 110% 硬上限
- 订阅制 Token 配额 + 余额兜底
- 汇率自动转换

**前端**:
- 58 个 HTML 模板，go:embed 嵌入单二进制
- HTMX 处理交互，Alpine.js 处理复杂 UI
- 支持 i18n（中/英）、主题（亮/暗/系统）、货币（CNY/USD）

### 3.3 start.sh 启动脚本

**功能完备度**: ⭐⭐⭐⭐⭐

支持 15+ 命令：`mvp`、`simulate`、`portal`、`proxy`、`stop`、`status`、`build`、`clean`、`clean-all`、`rebuild`、`logs` 等

**亮点**:
- 自动检测 Proxy 目录（同级/子目录/环境变量）
- 首次运行自动生成随机密钥（复用已有 .env）
- Proxy 自动检测 Portal 容器（单机部署自动使用容器名）
- 支持命令行参数覆盖（`--portal-url`、`--proxy-secret`、`--jwt-secret`、`--redis-password`）
- 健康检查等待（最多 30s）
- `clean-all` 清理 Docker 卷 + 构建产物 + 残留数据

**问题**:
- `set -e` 全局启用，任何命令失败立即退出（可能误杀后续清理逻辑）
- `clean-all` 中硬编码了 `/mnt/workspace/docker/volumes/` 路径（line 788-789）
- Proxy compose 中 `REDIS_HOST: redis` 指向容器名，但 Redis 可能不在同一网络

## 四、安全分析

### 4.1 安全评分

| 安全维度 | 评分 | 说明 |
|----------|------|------|
| **认证** | ⭐⭐⭐⭐ | JWT + HMAC + 多层 Key 验证；Portal 降级 30 分钟缓存 |
| **授权** | ⭐⭐⭐⭐ | 4 级角色（user → enterprise_admin → system_admin → super_admin） |
| **加密** | ⭐⭐⭐⭐⭐ | AES-256-GCM 存储加密、SHA-256 哈希、HMAC-SHA256 签名 |
| **输入验证** | ⭐⭐⭐⭐ | 参数化 SQL 防注入、NULL 字节过滤、请求大小限制 |
| **CSRF** | ⭐⭐⭐⭐ | Cookie + 表单双 Token 验证；API 用 JWT 天然免疫 |
| **XSS** | ⭐⭐⭐ | Go html/template 自动转义；但 CSP 允许 `unsafe-eval` |
| **限流** | ⭐⭐⭐⭐ | 多窗口 Token Bucket；但 Portal Admin 限流仅内存 |

### 4.2 安全隐患清单

#### 高优先级

| # | 问题 | 位置 | 风险 |
|---|------|------|------|
| H1 | Proxy dev_mode 模式接受任意 API Key | `proxy/internal/auth/auth.go:698-721` | 生产环境误开 dev_mode 将绕过所有认证 |
| H2 | Portal CSP 允许 `unsafe-eval` | `portal/internal/web/middleware.go:29` | Alpine.js 依赖，但削弱 XSS 防护 |
| H3 | ENCRYPTION_KEY 为空时 Proxy 启动失败 | `proxy/pkg/keypool/manager.go:421` | 正确设计；但 Portal 端未同步强制检查 |

#### 中优先级

| # | 问题 | 位置 | 风险 |
|---|------|------|------|
| M1 | Admin Secret 可降级为 Sync Secret | `proxy/internal/auth/auth.go:406-410` | 两个安全上下文共享同一密钥 |
| M2 | Portal 管理后台限流仅内存实现 | `portal/cmd/server/main.go:602-661` | 多实例部署时限流失效 |
| M3 | CSRF Cookie 未设 HttpOnly | `portal/internal/web/middleware.go:51` | XSS 可窃取 CSRF Token |
| M4 | `sk-` 前缀校验仅为格式检查 | `proxy/internal/auth/auth.go:185` | 非加密验证，可被伪造格式绕过 |

#### 低优先级

| # | 问题 | 位置 | 风险 |
|---|------|------|------|
| L1 | 模拟模式下验证码日志明文输出 | `portal/internal/routes/auth.go:133-135` | 仅开发环境，风险有限 |
| L2 | Affinity 缓存指纹仅 8 字符 | `proxy/pkg/cache/affinity.go:110` | 碰撞概率低但存在 |
| L3 | config.yaml 含占位密码 | `proxy/config.yaml:10` | 误部署将暴露数据库 |

### 4.3 安全设计亮点

1. **密钥加密存储**: API Key 使用 AES-256-GCM 加密后存入 Redis/PostgreSQL，内存中仅保留哈希
2. **Webhook 防重放**: 时间戳 ±300s + Nonce 校验
3. **启动时密钥校验**: Admin Secret、Sync Secret、Encryption Key 均强制 ≥32 字符
4. **余额实时拒绝**: Redis Pub/Sub 实现近实时余额不足拒绝（10s 缓存 + Pub/Sub 双保险）
5. **企业信用硬上限**: 110% cap 防止信用超支

## 五、业务模式分析

### 5.1 用户分层

| 用户类型 | Key 格式 | 计费模式 | Key 池优先级 |
|----------|----------|----------|-------------|
| **企业** | `sk-wgit-en-{uuid}` | 后付费信用额度 | high |
| **订阅** | `sk-wgit-tp-{uuid}` | Token/Code 月度配额 | high |
| **单模型** | `sk-wgit-{uuid}` | 单模型购买 + 余额兜底 | high |
| **普通** | `sk-wgit-{uuid}` | 余额扣费 | normal |
| **经济** | `sk-wgit-{uuid}` | 用户组折扣（默认 85%） | economy |

### 5.2 计费模型

**Proxy 侧**:
- 采集原始 Usage（input/output/cache tokens）
- 计算成本（基于 Portal 同步的定价）
- 异步批量上报 Portal

**Portal 侧**:
- 核算最终费用（使用 Portal 自身定价，非 Proxy 估算值）
- 支持 per-token 和 per-request 两种计费模式
- 三级余额扣除：Gift → Recharge → Balance
- 企业：Gift → Enterprise Credit (110% cap) → 无个人兜底
- 订阅：Token 配额优先 → 余额兜底

**缓存 Token 折扣**:
- Cache Read: 10% input 价格
- Cache Write: 25% input 价格
- 激励使用 Claude/OpenAI 的 Prompt Caching

### 5.3 限流体系

```
┌───────────────────────────────────────────┐
│              限流层级                       │
├───────────┬───────────┬───────────────────┤
│  Key 级   │  订阅级   │    用户组级        │
│  RPM/TPM  │  RPM/TPM  │  RPM/RPH/RPD...  │
├───────────┴───────────┴───────────────────┤
│         取最小值作为生效限制                 │
└───────────────────────────────────────────┘
```

**窗口维度**: RPM、RPH、RP5H、RPW、RPD、TPM、TPH、TPD、并发

### 5.4 路由策略

**Smart Route Chain**（无管理员手动配置时自动生效）:
1. **HEALTH**: 排除错误率 >80% 或 unhealthy 的 Key
2. **TIER**: premium > enterprise > default > economy
3. **RPM**: 排除已达 RPM 上限的 Key
4. **LATENCY**: 优先低延迟桶（<800ms / <2s / <5s / >5s）
5. **QUOTA**: 优先剩余配额多的 Key
6. **LRU + Affinity**: 最近最少使用 + Prompt Cache 亲和性

**跨 Provider 回退**: 当主 Provider 不可用时，自动尝试所有支持该模型的 Provider。

### 5.5 企业功能

- 企业级 Key 管理（企业范围隔离）
- 成员管理（enterprise_admin → manager → member）
- 成员配额上限
- 企业级定价比率覆盖
- 邀请流程（邮件 + 审批）
- 信用额度警报（80% / 90% / 100%）
- CSV 导出（Usage + Audit）
- 月度账单重置

## 六、代码质量评估

### 6.1 优点

| 方面 | 说明 |
|------|------|
| **参数化 SQL** | 全项目使用 `$N` 占位符，零 SQL 注入风险 |
| **并发安全** | Proxy Key 池使用分片锁 + 原子操作，无数据竞争 |
| **文档完备** | 90+ 篇设计/计划/报告文档，命名规范统一 |
| **测试覆盖** | Webhook 有专用测试套件，集成测试和性能测试完备 |
| **单一职责** | Proxy 无状态、Portal 管数据，职责清晰 |
| **优雅降级** | Portal 不可用时 Proxy 缓存延长至 30 分钟，服务不中断 |

### 6.2 需改进

| 问题 | 严重度 | 建议 |
|------|--------|------|
| **Route 文件过大** | 中 | admin.go (2902行)、enterprise.go (2888行) 应拆分 |
| **全局可变状态** | 中 | Proxy handlers.go 使用包级变量，建议依赖注入 |
| **缺少请求超时** | 中 | Portal DB 查询无 context.Timeout，慢查询可能阻塞连接 |
| **无熔断器** | 低 | Portal 缺少对 PostgreSQL 的熔断保护 |
| **CSP unsafe-eval** | 中 | 应消除 Alpine.js 的 eval 依赖 |
| **静态文件 Content-Type** | 低 | main.go 手动设置 MIME 类型，应使用 http.DetectContentType |
