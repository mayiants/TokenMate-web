## 2. 安全漏洞

### 2.1 🔴 CORS 配置缺陷（Portal）

| 项目 | 详情 |
|------|------|
| **文件** | `cmd/server/main.go` |
| **行号** | 498-545 |
| **状态** | ⏸️ **暂不修复**（用户要求上线测试后再处理） |
| **问题** | 当环境变量 `ALLOWED_ORIGINS` 为空时，`allowAll = true`，直接反射请求中的 `Origin` 头并允许访问。项目使用 Cookie 认证（JWT Cookie），**任意来源均可发起带凭据的跨站请求**。 |
| **风险** | 攻击者可构造恶意网页，利用用户的已登录 Cookie 调用管理 API（CSRF），或配合 XSS 窃取数据。 |
| **修复建议** | 1. 空 `ALLOWED_ORIGINS` 时拒绝启动或仅允许同源请求；2. 生产环境强制配置 `ALLOWED_ORIGINS`；3. Cookie 设置 `SameSite=Strict`（当前为 `Lax`）。 |

**佐证**：历史 code-review 文档 `docs/code-review-202605291412.md:95-102` 和 `docs/code-review-202605300413.md:36` 均记录此问题，状态为 **未修复**。

| **修复建议** | 在服务端统一实现与 `getPasswordRequirements` 声明一致的密码复杂度校验函数，三个接口均调用该函数。 |

### 2.6 🟡 SSRF 风险 - BaseURL 未校验（Proxy）

| 项目 | 详情 |
|------|------|
| **文件** | `internal/server/admin_handlers.go` |
| **行号** | 182, 300（admin_handlers） |
| **状态** | ✅ **已修复**（2026-06-01） |
| **修复内容** | 新增 `validateBaseURL()` 函数，校验规则：必须有 scheme、禁止 localhost/127.0.0.1/0.0.0.0/::1、禁止 169.254.x.x 元数据地址、禁止私有 IP（10.x/172.16-31.x/192.168.x）。在 `handleAddKey` 和 `handleImportKeys` 中调用，非法 BaseURL 返回 400。 |
| **问题** | 多处通过 `http.NewRequest` 向外部 URL 发送请求。`upstreamBaseURL` 来自 `upstreamKey.BaseURL`（可通过 Admin API `/admin/keys` 设置），`Portal.URL` 来自配置，均未校验目标地址是否指向内网（`169.254.169.254` 元数据服务、`10.0.0.0/8` 等）或元数据服务。 |
| **风险** | 攻击者通过 Admin API 设置 BaseURL 为 `http://169.254.169.254/latest/meta-data/iam/security-credentials/`，窃取 EC2 IAM 临时凭证。 |
| **修复建议** | 1. 对所有外部 URL 进行 SSRF 过滤，禁止访问内网 IP、元数据地址、localhost；2. 提供 URL 白名单机制；3. Admin API 修改 BaseURL 时需额外权限校验。 |

### 2.9 🟡 时序攻击 - 字符串比较（Proxy）

|------|------|
| **文件** | `internal/routes/auth.go` |

|------|------|

### 3.5 API Key 暴露在 URL Query（Portal）

| 项目 | 详情 |

| **问题** | `c.Query("api_key")` 直接从 URL Query 参数读取上游 Provider 的 API 密钥。 |
| **风险** | API 密钥暴露在 URL 中，会被浏览器历史、代理日志、Referer 头记录。 |
| **修复建议** | 改为从 POST Body 或 Header 中读取，URL 中不应包含任何敏感凭证。 |

## 5. 代码质量问题

### 5.1 错误处理不一致

**问题概述**：两个项目都存在错误处理风格不一致的问题：

| 项目 | 表现 |
|------|------|
| Portal | 部分接口返回 `{"error": "具体错误"}`，部分返回 `{"message": "具体错误"}`，部分返回 `{"detail": "..."}` |
| Proxy | 部分返回 `{"error": err.Error()}`，部分返回结构化错误，部分静默忽略错误 |

**修复建议**：统一错误响应格式，建议采用：

```json
{
  "error": {
    "code": "invalid_request",
    "message": "通用错误描述（可翻译）",
    "detail": "内部排查用详情（仅开发环境返回）"
  }
}
```
